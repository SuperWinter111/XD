# BMS 技术栈与技术架构基线

本文档用于回答三个问题：

1. 后续开发是否需要先确认技术选型。
2. 在当前阶段，哪些技术决策必须先冻结。
3. 在用户偏好 C++ 的前提下，当前仓库的默认工程技术基线是什么。

## 1. 结论

需要确认，但不需要把所有技术问题一次性定死。

当前建议采用两层决策：

1. 先冻结最小工程基线。
2. 再把供应商相关、平台相关和部署相关决策延后到联调前。

## 2. 当前应先冻结的技术决策

以下内容建议现在就确认：

1. 主开发语言：C++。
2. 语言标准：C++20。
3. 构建系统：CMake。
4. schema/IDL 主来源：proto 目录下的 .proto 文件。
5. 代码组织方式：按 workPackage 建独立 implementation 子目录。
6. 测试组织方式：每个 workPackage 独立 tests 目录。

## 3. 当前可以暂缓的技术决策

以下内容不必在首个开发包启动前完全定死：

1. 具体 DDS 中间件供应商。
2. 是否引入统一依赖管理工具。
3. CI/CD 平台选型。
4. 运行时容器编排方式。
5. 正式日志框架和监控 SDK 的最终选型。

## 4. 推荐技术基线

在当前仓库下，建议先采用以下默认技术基线：

1. 编程语言：C++20。
2. 构建系统：CMake 3.20+。
3. 目录结构：implementation/wpXX_xxx/。
4. schema 来源：proto/bms/schema/*.proto。
5. 序列化模型：以 proto 生成代码为目标，但首批骨架先与生成代码解耦。
6. 单元测试：先使用零外部依赖 smoke test 骨架，后续再引入 GoogleTest。
7. 运行时消息适配：先定义抽象端口，不绑定具体 DDS vendor。

## 5. 当前技术架构建议

当前建议采用“分层 + 端口适配”方式：

1. domain 层：定义 TopicRegistry、SubscriptionRegistry、EnvelopeRouter 等核心服务。
2. application 层：组织注册、路由、回执、重试流程。
3. adapter 层：后续对接 DDS、日志、监控、持久化。
4. test 层：以契约样例和 smoke test 驱动。

## 6. 对 C++ 偏好的具体落地

既然你的编程语言偏好是 C++，当前就按 C++ 基线落地首个开发包。

这意味着：

1. 首个 implementation 工程将使用 CMake + C++20。
2. proto 作为后续生成 C++ 类型的权威来源。
3. 工程级 ICD 与 C++ 代码骨架并行维护。

## 7. 一句话原则

当前需要确认的是“最小可开发技术基线”，而不是在首包启动前把所有基础设施选型一次性做完。
