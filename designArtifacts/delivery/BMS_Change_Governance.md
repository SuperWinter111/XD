# BMS 设计变更治理

本文档用于约束跨分系统设计变更的提出、评估、批准、发布与回滚流程，避免在 schema、ICD、topic、ownership、组件边界上发生无控制漂移。

## 1. 适用范围

以下变更必须纳入治理：

1. 公共 schema / proto 结构变更。
2. 正式 ICD 语义、字段、时序、错误码、拒绝条件变更。
3. topic 名称、QoS、publisher、consumer 关系变更。
4. 主对象 ownership 变更。
5. Container、Component、Code 图边界变更。
6. 工作包范围、联调入口、验收口径变更。

## 2. 标准流程

1. 提出变更：说明变更原因、影响对象、影响链路、兼容策略。
2. 影响分析：识别受影响的分系统、正式 ICD、schema、工作包、联调场景。
3. owner 确认：由主拥有者和直接上下游共同确认。
4. 文档更新：同步更新 guide、traceability matrix、相关 ICD、相关工作包。
5. 版本发布：记录版本号、生效时间和回滚方式。
6. 联调复核：对受影响链路至少执行 1 套回归样例。

## 3. 最小变更记录

每次受治理变更至少要记录：

1. 变更标题。
2. 变更类型。
3. 发起人。
4. 主 owner。
5. 受影响文档。
6. 受影响分系统。
7. 兼容策略。
8. 回滚策略。
9. 验证结果。

## 4. 兼容性规则

1. 公共 payload 增字段优先采用向后兼容方式。
2. 删除字段、重命名 topic、改变 ownership 一律视为高风险变更。
3. 高风险变更未完成影响分析前，不得直接进入实现。
4. 若上下游版本窗口不能同步，必须给出临时兼容或双写策略。

## 5. 禁止事项

1. 禁止未更新文档先更新公共接口实现。
2. 禁止分系统私下协商新增未登记 topic。
3. 禁止在未确认 owner 的情况下改写主对象语义。
4. 禁止把仿真约束、边缘适配细节或临时 mock 直接固化为系统级正式语义。

## 6. 文档联动要求

若变更类型为下列内容，至少应同步更新对应文档：

1. ownership 变更：BMS_Owner_Rule_Baseline、对象目录、工作包。
2. 完成标准变更：BMS_Completion_Definition、执行手册、工作包模板。
3. topic / payload 变更：DDS_Topic_Catalog、正式 ICD、相关工作包、联调矩阵。
4. 架构边界变更：C4 图、Code 图、追踪矩阵、交付包清单。
