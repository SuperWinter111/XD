# 旧系统 ICD 参考评估

本文档用于说明 oldSysReference 目录下旧系统 ICD 对当前 BMS 正式 ICD 设计的参考方式、可借鉴内容与禁止直接继承的内容。

适用文件：

1. oldSysReference/EnhanceUnit.txt
2. oldSysReference/bms_type.txt

## 1. 结论

结论如下：

1. 两份旧文件可以作为当前正式 ICD 的参考资料。
2. 参考重点应放在接口颗粒度、字段量纲、状态口径、时间字段、编号长度、上下行拆分方式。
3. 不应把旧文件作为当前系统的语义主来源。
4. 不应大规模照搬旧对象命名、旧消息拆分、旧任务语义和旧目标语义。

## 2. 两份旧文件的角色判断

### 2.1 EnhanceUnit.txt

这份文件更接近：

1. 协同增强单元与无人机之间的边缘二进制协议草案。
2. 平台控制、平台状态、传感器控制、图片传输、目标上报的混合接口清单。

它对当前设计最有价值的部分是：

1. 上下行边界清晰。
2. 平台状态字段粒度较工程化。
3. 经纬高、速度、姿态、任务状态等量纲写得比较实。
4. 航路点级别控制颗粒度比较明确。

它的问题也很明显：

1. 任务、平台、目标、载荷、图片流、打击结果混在一起。
2. 消息编号、帧结构、PHYID 与当前内部 DDS/schema 语义层不是一层东西。
3. 有明显的字段编号错乱与注释错位。
4. 同一对象在不同消息中的字段口径不完全一致。

因此它应只作为边缘接口颗粒度与工程字段参考，不作为核心业务 schema 蓝本。

### 2.2 bms_type.txt

这份文件更接近：

1. 旧系统跨分系统数据结构头文件。
2. 旧业务对象、旧任务对象、旧目标对象、旧平台对象的混合 C++/MsgPack 结构定义。

它的价值主要在：

1. 暴露了旧系统对象曾经拆到什么粒度。
2. 说明了平台属性、平台状态、目标属性、目标状态、任务状态、任务方案、区域等对象的工程字段范围。
3. 说明了旧系统中常见的状态码、目标属性项、任务属性项和区域属性项。

它的风险更大：

1. 目标属性、目标状态、任务语义、任务指令、任务方案存在高度耦合。
2. 同名对象在文件内部也存在重复、扩展、补丁式演化痕迹。
3. 某些对象明显是程序实现妥协，不是稳定 ICD 语义。
4. 某些字段带有旧系统专有场景假设，不适合作为新系统标准字段。

因此它应只作为对象粒度参考与字段补充候选池，不作为正式 ICD 的直接来源。

## 3. 可借鉴内容

### 3.1 可以直接借鉴的方法层内容

1. 明确区分平台状态、平台属性、目标状态、目标属性、任务状态、任务指令。
2. 为每个状态或命令补充更细的单位、范围、比例尺、时戳口径。
3. 为平台、目标、任务、区域保留稳定编号字段。
4. 对于边缘接口，保留上行状态与下行控制的显式分离。

### 3.2 可以吸收到当前正式 ICD 的字段颗粒度

可考虑吸收进当前正式 ICD 的字段方向包括：

1. 平台状态中的剩余油量或剩余电量、剩余航时、健康状态、地速、北向速度、东向速度、姿态角。
2. 平台属性中的动力类型、最大航时、巡航速度、升限、抗风等级。
3. 目标属性中的阵营、时敏特征、机动能力、探测方式、防护能力、电磁特征、外形尺寸。
4. 目标状态中的毁伤状态与坐标系统字段。
5. 任务状态中的进行中、暂停、终止、完成、失败等口径。
6. 航路点中的点类型、时刻、速度、方向。

### 3.3 可以吸收到协同增强单元边缘接口设计的工程约束

1. 经纬高单位、范围、比例尺必须写清。
2. 视频、图片、目标、平台状态不能再只写成抽象对象，必须补充边缘侧传输口径。
3. 命令应答、航线执行状态、投放结果、目标打击结果需要有单独 topic 或单独 payload。
4. 平台与载荷控制应继续保持分离，不要混成一个万能控制消息。

## 4. 不可直接照搬内容

### 4.1 不可照搬的语义

1. 旧系统中的任务类型枚举。
2. 旧系统中的目标类型表。
3. 旧系统中的平台属性分类值。
4. 旧系统中把任务方案、任务决策、平台分配、区域划分混成一层对象的写法。

原因：

1. 当前系统已经建立了 Task、Plan、Execution、Resource、Situation 的分层边界。
2. 旧系统对象边界明显跨层，直接照搬会破坏现有正式 ICD 的语义分层。

### 4.2 不可照搬的技术层内容

1. 帧头、帧计数、帧 ID、校验、PHYID。
2. MsgPack 序列化细节。
3. 旧系统的固定 20 个航点、固定 40 字节 ID、固定数量平台数组等实现限制。

原因：

1. 这些属于旧协议实现层，不应污染当前系统的内部标准对象。
2. 当前系统内部对象应先表达语义，再由 EnhanceUnit 或协议桥负责映射到具体协议。

## 5. 对当前正式 ICD 的直接启发

### 5.1 平台执行链

对 designArtifacts/icd/BMS_ICD_Formal_01_Platform_Execution_Chain.md 的启发：

1. 需要继续补平台速度分量、姿态、健康、能源余量口径。
2. 需要继续明确载荷控制与武器控制的边缘命令拆分。
3. 需要为航路执行状态与命令应答补更细的边缘工程约束。

### 5.2 任务计划执行闭环

对 designArtifacts/icd/BMS_ICD_Formal_02_Task_Battle_Execution_Closure.md 的启发：

1. 任务状态枚举可以进一步工程化。
2. 执行进度与航线执行状态应建立更清晰映射。
3. effect_report 后续可以参考旧系统的目标状态和目标打击结果字段做细化，但不能直接继承旧 target 语义。

### 5.3 资源调度专题

对 designArtifacts/icd/BMS_ICD_Formal_03_Resource_Allocation_And_Reservation.md 的启发：

1. 资源能力粒度可以参考旧平台属性和武器属性，但需要保留当前 owner 边界。
2. 平台属性、载荷能力、武器能力应继续拆分，不宜重新混成一个平台大对象直接跨域传输。

## 6. 后续使用原则

在后续正式 ICD 编写中，统一采用以下使用规则：

1. 先看当前 BMS 语义边界是否已有正式对象。
2. 若已有正式对象，只允许从旧 ICD 中借字段颗粒度与约束，不允许反向改坏对象边界。
3. 若当前对象尚未工程化完成，可从旧 ICD 中抽取候选字段，但必须重新归类到当前系统语义层。
4. 若旧 ICD 中字段仅属于协议适配层，则只进入 EnhanceUnit 或协议桥映射说明，不进入核心 schema。

## 7. 当前建议

建议下一步优先做以下两件事：

1. 用旧系统参考继续细化平台执行链专题中的边缘状态与命令口径。
2. 用旧系统参考继续细化态势与威胁专题，但只吸收目标属性颗粒度，不继承旧目标模型。
